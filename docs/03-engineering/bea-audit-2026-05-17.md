## Auditoria por área

### 1. Pipeline de resposta

**Como funciona (do trigger ao reply):**

1. Mensagem `incoming` do paciente cria row em `messages` → `Message.after_create_commit :trigger_ai_agent_listener` ([engine.rb:211](../../plugins/ai_agent/lib/ai_agent/engine.rb#L211))
2. `MessageListener#message_created` ([message_listener.rb:29](../../plugins/ai_agent/app/listeners/ai_agent/event_listeners/message_listener.rb#L29)) aplica filtros: `incoming?`, **sender é Contact real**, **não-`sent_via_api`**, não-privada, texto/mídia processável, Bea ativa, inbox vinculado a Beatriz, conversa não-escalada, sem assignee humano
3. `RateLimiter.check_and_increment` em Redis — com telemetria de hits separada
4. Job enfileirado com 3s de delay (debounce contra burst do WhatsApp)
5. `ChatResponseJob#perform` faz coalescing (mensagem mais nova vence), **idempotency check por `message_id`**, chama `ChatService#respond`
6. `ChatService` orquestra LLM + tools + guardrails → reply postado como `outgoing` via `AgentBotIdentity`

**Pontos fortes:**
- Deduplicação tripla (coalescing + Trace idempotency em SELECT + **unique index DB**)
- Bea nunca responde a si mesma (filtro `incoming?` + validação de sender)
- **Bea nunca responde a bot externo** (validação `sender_type == 'Contact'`)
- Hooks no core dedupados com `unless method_defined?` em todos os `class_eval` críticos
- Debounce de 3s absorve burst de mensagens fragmentadas do WhatsApp

**Riscos remanescentes:**
- Hooks no `to_prepare` podem stackar em reload travado (raro mas possível)
- Blob retry sem checar se conversa virou `escalated` no meio do retry
- Rate limiter Redis-dependent sem circuit breaker

### 2. Tools, Guardrails e Emergência

**Inventário das 21 tools** (todas registradas em `ToolRegistry`):

Mesma lista da v1 — `book_appointment`, `reschedule_appointment`, `cancel_appointment`, `clinic_info`, `search_available_slots`, `search_knowledge`, `transfer_to_human`, `patient_lookup`, `list_appointments`, `financial_status`, `notify_staff`, `erasure_request`, `find_patient_by_phone`, `confirm_patient_identity`, `create_patient_minimal`, e os 5 `internal_*` pares.

**Camadas de segurança (ordem de execução):**

```
PRÉ-LLM:
  1. Emergency::Detector (regex PT-BR: sangramento/AVC/suicídio) → SAMU/CVV
  2. EscalationRules (5 sinais: pedido humano, urgente, negativo 2×, tool fail 2×, repetição 5×)
  3. StateMachine::ConversationContext (confirma oferta pendente sem chamar LLM)

DURANTE LLM:
  4. ToolRegistry (21 tools, enabled/disabled via account whitelist)
  5. Critique determinístico (pré-execução em book/reschedule) — AGORA com service_id check
  6. Tool wrapping (auto-inject patient_id, override service_id)

PÓS-LLM:
  7. Guardrail::Validator (diagnóstico/prescrição/garantia) — AGORA com 6 patterns extras PT-BR
  8. Detectors (OffensiveTone, RefundRequest, EvasiveResponse) → notificações internas
  9. Sentinel (LLM-as-judge, feature-flagged) — agora COM visibilidade no boot + dashboard
  10. Trace + State persistence — Trace com message_id, índice único parcial
```

**Buracos remanescentes:**
- Emergency com janela 80 chars (problema #5 acima — pendente, Tier 3)
- Loop infinito em ambiguidade de paciente (família com 2+ Patients no mesmo WhatsApp) — depois de 3 tentativas, estado não resetta (Tier 3)

**Tools órfãs ou redundantes:** nenhuma órfã. Os 5 pares `internal_*` continuam intencionais.
